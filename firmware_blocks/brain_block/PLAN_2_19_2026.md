# Brain-to-LED Flash Event Path Review and Test-Readiness Plan

## Summary
Your current structure is close to the intended architecture (Brain orchestrates, LED block executes locally), and the event pipeline is present end-to-end.  
The main blockers before reliable testing are status-flag semantics and I2C concurrency control on the Brain side.

## Current Findings (ordered by severity)

1. **`STATUS_DATA_READY` is being asserted for non-event commands on LED block**
- `firmware_blocks/block_templates/led_color_flash_block/main/command_handler.c:397`
- `firmware_blocks/block_templates/led_color_flash_block/main/command_handler.c:403`
- Brain polls `REG_STATUS` and treats `DATA_READY` as “event pending” (`firmware_blocks/brain_block/main/main.c:43`), so this can cause repeated `CMD_GET_DATA` polling with no event payload.

2. **Brain has multiple concurrent I2C callers without a bus lock**
- Registry scanner: `firmware_blocks/brain_block/main/main.c:17`
- Event poller: `firmware_blocks/brain_block/main/main.c:26`
- Demo task I2C traffic: `firmware_blocks/brain_block/main/demo_task.c:31`
- TCP/config scanner also triggers scans: `firmware_blocks/brain_block/main/block_config_manager.c:143`
- This can create nondeterministic ACK/timeouts during bring-up.

3. **Architecture doc and implementation are out of sync for SUBMIT behavior**
- Doc says submit queues execute locally: `firmware_blocks/block_templates/led_color_flash_block/ARCHITECTURE.md:75`
- Actual code (and selected intent) is Brain-authoritative submit-event flow: `firmware_blocks/block_templates/led_color_flash_block/main/tft_ui.c:146`

4. **Event handling resilience gaps**
- Event enqueue failures are silently ignored by caller in Brain poll loop (`firmware_blocks/brain_block/main/main.c:49`).
- No explicit guard/logging for malformed payload lengths in Brain poll path (`firmware_blocks/brain_block/main/main.c:47`).

5. **Minor clarity issue**
- Comment range in registry implementation is stale (`firmware_blocks/brain_block/main/device_registry.c:5`), though header range is correct (`firmware_blocks/brain_block/main/device_registry.h:16`).

## Implementation Plan (decision-complete)

1. **Normalize LED block status semantics**
- In `command_handler.c`, only set `STATUS_DATA_READY` when `s_pending_event_valid == true` (submit event pending).
- For `CMD_SET_LED` payload updates, set status to `STATUS_READY` unless an event is pending.
- Keep `STATUS_BUSY` strictly for in-flight action worker execution.

2. **Add a Brain-side I2C master mutex and enforce it**
- Introduce a static mutex in Brain I2C layer (`firmware_blocks/brain_block/main/i2c_comm.c`).
- Wrap all master transactions (`i2c_ping`, `i2c_read_reg`, `i2c_get_data`, command sends) with lock/unlock.
- Keep call sites unchanged to minimize integration risk.

3. **Harden event poll/forward path**
- In `block_event_poll_task`, validate `i2c_get_data` result length expectations (2-byte event frame).
- Log and skip on malformed frames.
- Check return of `brain_event_handle_block_event(...)`; warn on queue-full/reject.
- Optionally include one retry for transient queue-full if non-blocking behavior is still desired.

4. **Align architecture docs with selected behavior**
- Update `ARCHITECTURE.md` UI submit section to state:
  - submit publishes event (`STATUS_DATA_READY` + payload),
  - Brain decides orchestration and sends execute commands back.

5. **Reduce bring-up noise for deterministic tests**
- Gate or remove unconditional `i2c_safe_scan()` inside `demo_task` loop (`demo_task.c:31`) during event-path testing mode.
- Keep periodic registry scans, but ensure they do not starve event polling via mutex-protected short transactions.

## Public Interfaces / Types to Add or Adjust

1. **Shared event ID contract in protocol header**
- Add a shared event enum/defines in `firmware_blocks/include/i2c_protocol.h`:
  - e.g., `BLOCK_EVENT_SELECTION_SUBMIT = 0x01`
- Use it in both:
  - LED block `command_handler.c`
  - Brain `brain_event_handler.h/.c`
- This removes duplicated literal/event defines.

2. **No wire-format change**
- Keep payload format as `[event_id, event_value]` (2 bytes) for current implementation.

## Test Cases and Scenarios (Brain + LED block only)

1. **Discovery and identity**
- Power both boards, verify Brain registry sees LED block with `WHOAMI=BLOCK_TYPE_LED_FLASH`.
- Pass criteria: consistent detection across 10 scans without intermittent unknown type.

2. **Submit event lifecycle**
- On LED block UI: tap digit then `SUBMIT`.
- Brain should read `STATUS_DATA_READY`, issue `CMD_GET_DATA`, receive `[0x01, digit]`.
- Pass criteria: one submit produces one event consumption; `DATA_READY` clears after fetch.

3. **Brain-authoritative execute**
- After receiving submit event, Brain issues `CMD_SET_LED` then `CMD_EXECUTE` to same address.
- LED block runs mapped effect; status transitions `READY -> BUSY -> READY`.
- Pass criteria: effect matches selected digit and logs show ordered command sequence.

4. **Busy-path rejection**
- Trigger long effect (e.g., 7/8/9), press submit repeatedly during execution.
- Pass criteria: child rejects submit while busy (no extra event frames), UI shows busy feedback.

5. **Concurrency stability**
- Run for 5-10 minutes with periodic scans enabled.
- Pass criteria: no I2C timeout storms, no repeated empty `GET_DATA` loops, no missed submit events.

## Assumptions and Defaults Chosen

- **Chosen behavior:** Brain-authoritative submit flow (as confirmed).
- **Available hardware:** Brain + LED block only (as confirmed).
- Keep existing I2C addressing unless board-level conflicts are observed.
